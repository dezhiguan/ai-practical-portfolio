> 仅记录影响范围、顺序或边界的**重要决策**及原因。任务级细节见 [ai-common-infra-development-plan.md](./ai-common-infra-development-plan.md)。

## 2026-05-20：三部分组成，先底座后业务

**决策：** 通用 AI 技术底座 → 小红书工作台 → 求职 Agent 工作台 → 能力增强。

**原因：** 共用 AI 调用、日志、成本、失败处理；先底座避免重复建设且行为一致。

---

## 2026-05-20：AI 辅助 + 人工确认，不做高风险自动化

**决策：** 辅助生成与分析由系统完成；发布、投递、对外回复由用户执行。不做自动登录/发布/抓取/回复 HR、绕过风控等。

**原因：** 平台规则与误操作风险高；项目目标是稳定、可控、可复用的 AI 工程能力。

---

**原因：** 周期长、易中断，需可恢复的上下文与职责边界。

## 2026-05-21：底座逻辑分层与编排中枢

**决策：** 采用「接入层 → 编排层（AI Gateway）→ 路由/韧性/观测/供应商访问 → 配置与持久化」四层逻辑划分；**AI Gateway** 作为单次调用的编排中枢，**Model Router** 只负责选计划模型，**Model Client** 只负责单次供应商调用，**Retry** 与 **Degradation** 分离（先同模型重试，再按备用模型降级）。

**原因：** 与需求 4.1～4.5 职责边界一致，避免 Router/Client 膨胀；便于 T-014～T-033 分任务实现与单测。

---

## 2026-05-21：第一阶段同步调用 + 静态路由

**决策：** 第一阶段以业务后端 → Gateway 的**同步调用语义**为主；路由为**配置驱动静态策略**，不做动态选模与 Agent 编排。

**原因：** 对齐需求第八章「不做什么」；降低首版复杂度，满足 AC-1～AC-7 即可验收。

---

## 2026-05-21：业务复用契约

**决策：** 两业务系统仅通过 Gateway 统一语义接入；必须携带 `businessType` + `projectId`；Agent 多步编排留在业务域，每步 LLM 仍逐步调 Gateway。

**原因：** 满足 AC-7 与需求 6.2～6.3；防止业务侧复制降级/成本逻辑。

---

## 2026-05-21：调用日志采用主表 + 尝试明细表

**决策：** `ai_invocation_log` 每次请求一条主记录；`ai_invocation_attempt` 记录每次模型调用（重试/降级链）。失败信息写入主表 + 尝试表，**不单独建失败事实表**。

**原因：** 满足 AC-3 降级链路可追溯；AC-4 可对主表失败字段聚合；避免三表同步冗余。

---

## 2026-05-21：关系型库 + 日志默认不存全文

**决策：** 第一阶段使用关系型数据库存储配置与调用事实；`ai_invocation_log` 默认仅存输入/输出长度与可选截断预览，不存完整 Prompt/生成全文与 API Key。

**原因：** 满足安全与脱敏要求；列表/统计以结构化字段为主；全文审计列为后续扩展。

---

## 2026-05-21：日成本用量表

**决策：** 增加 `ai_quota_usage_daily` 累加当日估算成本，配合 `ai_quota_policy` 实现日成本上限快速判断；Token/成本多维汇总第一阶段对 `ai_invocation_log` 聚合，性能不足再引入 `ai_stats_daily`。

**原因：** 满足 AC-6 前置检查性能；控制首版表数量。

---

## 2026-05-21：API 路径与 Invoke 语义分离

**决策：** 业务调用 `POST /api/v1/ai/invoke`；管理观测统一前缀 `/api/v1/admin/*`。供应商调用失败时 HTTP 仍 200，`code=0`，失败放在 `data.status` + `data.failure`；仅参数/鉴权/限流/成本前置拦截用非 0 `code`。

**原因：** 与 T-005 响应语义一致；业务后端便于统一解析成功包络；日志必落库（AC-1）。

---

## 2026-05-21：调用链鉴权与前端边界

**决策：** Invoke 使用 `X-Internal-Api-Key` 供业务后端调用；禁止业务前端直连 Invoke；禁止任何前端直连大模型。

**原因：** 对齐架构 §2.3 与项目红线；密钥不暴露给浏览器。

---

## 2026-05-21：全项目技术栈基线

**决策：** 后端统一 **Java 17 + Spring Boot 3.x + MySQL 8**；前端统一 **Vue 3 + TypeScript + Vite + Element Plus**（分阶段建设）；AI 采用**自研 Gateway + HTTP Provider Adapter**，第一阶段不引入 Spring AI / Agent 框架 / Redis / RAG。

**原因：** 与 guideline「基于 Java 技术栈」一致；控制首阶段复杂度；底座与业务职责边界清晰。

---

## 2026-05-21：RAG 与 Agent 技术延后

**决策：** RAG 仅在第三阶段 `smart-job-agent` 引入，推荐 **PostgreSQL + pgvector + Tika + Embedding API**；Agent 采用**业务内工作流表 + 状态机**，每步 LLM 仍调底座 Invoke；不使用 LangChain4j 作为首版方案。

**原因：** 需求与架构明确底座不含 RAG/编排；避免过早引入向量库与 Agent 框架运维成本。

---

## 2026-05-21：缓存与文件存储分阶段

**决策：** 第一阶段限流/熔断/配置缓存用 **Caffeine 单机内存**；Redis 延后至多实例或业务 Session 需要时。文件存储：底座无；小红书第二阶段 **本地目录 + MinIO（推荐）** 存素材。

**原因：** 单人/小团队、单机部署足够；符合「不过度设计」原则。
