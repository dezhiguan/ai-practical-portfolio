## 二、架构目标

### 2.1 整体目标

建设一套**可复用、可观测、具备韧性**的 AI 调用基础设施，使所有业务系统通过**单一入口**使用大模型能力，而无需各自实现路由、日志、成本、失败处理与供应商适配。

### 2.2 设计目标（可度量方向）

| 目标 | 说明 |
|------|------|
| 解耦供应商 | 业务与求职/小红书模块只依赖统一调用语义，不绑定任一模型 API |
| 统一观测 | 任意一次调用可通过请求编号关联日志、Token、成本、失败与降级链路 |
| 提高可用性 | 可重试错误自动重试；主模型不可用时按策略降级至备用模型 |
| 成本可控 | 多维度统计 + 日成本上限等基础防护，避免调用失控 |
| 边界清晰 | 底座不承担 Prompt 管理、Agent 编排、RAG、业务领域逻辑 |
| 可扩展 | 新增业务类型、模型供应商、路由规则时，业务系统无需复制底座能力 |

### 2.3 架构原则

1. **所有 AI 调用必经底座**：业务后端不得直连模型供应商；业务前端不得直连大模型。
2. **同步调用为主**：第一阶段以「业务发起 → 底座编排 → 返回结果」的同步语义为主；长任务与流式输出在接口设计阶段再细化，架构上预留扩展点即可。
3. **配置驱动路由**：第一阶段采用静态配置（业务类型 → 主/备模型），不做运行时动态选模。
4. **失败可分类、可聚合**：失败类型统一枚举，支撑重试/降级决策与管理端统计。
5. **敏感信息隔离**：密钥、完整隐私请求体不进入业务可见日志与管理端详情。

### 4.2 模块边界（对内划分）

| 逻辑模块 | 职责摘要 | 边界：不负责 |
|----------|----------|----------------|
| **AI Gateway** | 唯一对外调用入口；组装请求上下文；驱动编排；返回统一响应语义 | 不解析业务领域 Prompt 模板；不执行业务 CRUD |
| **Model Router** | 按业务类型与策略选择计划模型（主模型）；读取主备配置 | 不发起 HTTP；不记录持久化日志 |
| **Model Client** | 对选定模型发起实际调用；解析供应商响应为统一内部结果 | 不做路由决策；不做跨模型降级循环 |
| **Provider Adapter** | 屏蔽各供应商请求/响应差异 | 不含路由、重试策略 |
| **Retry Handler** | 对可重试错误按策略重试（含退避） | 不处理不可重试类错误；不替代降级 |
| **Degradation Handler** | 主模型失败且满足条件时，按备用顺序切换模型并重试调用链 | 不对认证/参数/内容安全类错误换模型 |
| **Invocation Logger** | 每次调用（含重试、降级）写入完整调用记录 | 不做业务报表导出 |
| **Failure Tracker** | 失败分类、失败记录、聚合查询支撑 | 不替代业务侧用户提示文案 |
| **Token & Cost Service** | Token 归集、单价估算、多维度汇总 | 不做财务结算、多租户账单 |
| **Rate Limiter** | 全局、按业务类型（及后续按用户）限流 | 不替代供应商侧限流 |
| **Circuit Breaker** | 模型/供应商连续失败时暂停转发 | 不自动修改路由配置 |
| **Cost Guard** | 日成本上限等防护，超限拒绝并记录 | 第一阶段不做复杂动态定价 |
| **Admin / Observability** | 管理端 API + 页面所需查询与配置 | 不含小红书/求职业务页面 |
| **Config Registry** | 模型列表、路由表、单价、阈值等配置加载 | 第一阶段不做可视化拖拽配置中心 |

### 4.3 模块边界（对外）

| 外部系统 | 允许 | 禁止 |
|----------|------|------|
| 小红书 / 求职 Agent 后端 | 调用底座统一 AI 接口；传入业务类型、项目标识、用户标识、输入内容 | 直连 OpenAI/其他供应商 API；自建 Token 统计与降级逻辑 |
| 业务前端 | 调用各自业务后端 | 直连大模型 |
| 底座管理端 | 查询日志/统计；修改日成本上限等约定配置 | 承载业务素材、岗位、草稿等功能 |

## 五、核心组件职责

### 5.1 AI Gateway（统一 AI 网关）

**定位：** 底座对业务系统的**唯一入口**，也是单次 AI 调用的**编排中枢**。

**职责：**

1. 接收业务调用请求，校验必填语义（业务类型、输入内容等）。
2. 生成或承接**请求编号**，作为全链路追溯主键。
3. 在调用模型前执行**成本防护、限流**等前置检查。
4. 调用 **Model Router** 获取计划模型，再驱动 **Model Client** 执行；协调 **Retry**、**Degradation**。
5. 调用结束后触发 **Invocation Logger**、**Token & Cost**、**Failure Tracker** 写入。
6. 向业务方返回统一响应语义（状态、输出、Token、估算成本、实际模型、失败信息等）。

**不负责：** 业务场景内的 Prompt 拼装策略（由业务模块完成后再作为输入传入）；Agent 多步编排。

---

### 5.2 Model Router（多模型路由）

**定位：** 根据**业务类型**与静态策略，决定**本次调用的计划模型**（主模型）。

**职责：**

1. 读取配置：业务类型 → 主模型、备用模型列表、低成本/高能力策略标记。
2. 结合 **Cost Guard** 约束（如是否允许高成本模型）输出计划模型。
3. 结合 **Circuit Breaker** 状态：若主模型熔断中，可直接选用备用或标记需走降级路径（与 Degradation 协同）。
4. 将路由决策（业务类型、计划模型）交给编排层记录。

**不负责：** 实际 HTTP 调用；重试次数控制；日志持久化细节。

---

### 5.3 Model Client（模型客户端）

**定位：** 对**某一个具体模型**执行一次供应商调用，返回统一的内部调用结果。

**职责：**

1. 通过 **Provider Adapter** 将统一内部请求转换为供应商格式。
2. 发起调用并处理超时（超时阈值来自配置）。
3. 将供应商响应转换为统一结构：成功内容、Token 数（若可得）、原始错误信息等。
4. 将供应商错误映射为统一**失败类型**，供 Retry / Degradation / Failure Tracker 使用。

**不负责：** 在多个模型之间切换；业务类型路由。

---

### 5.4 Provider Adapter（供应商适配层）

**定位：** 位于 Model Client 之下，**按供应商**实现差异屏蔽。

**职责：**

1. 认证方式、端点、请求体、响应体字段映射。
2. 将供应商特有错误码映射为底座失败类型。

**边界：** 每新增一个供应商增加一个适配实现，不改动 Gateway 与 Router 的对外语义。

---

### 5.5 Invocation Logger（调用日志）

**定位：** 每一次 AI 调用的**事实记录**，支撑排查与审计。

**职责：**

1. 在调用生命周期结束时（成功、失败、降级成功）写入一条完整记录。
2. 记录需求文档 4.7 所列要素：请求编号、项目/用户/业务类型、计划与实际模型、状态、Token、估算成本、耗时、重试次数、是否降级、失败类型与详情（脱敏）等。
3. 为管理端列表/详情查询提供数据源。

**与 Failure Tracker 关系：** 失败调用在日志中必有记录；Failure Tracker 侧重失败分类与聚合统计，二者共享同一请求编号，可引用同一条日志或关联失败子记录（实现阶段在数据库文档定义）。

---

### 5.6 Token & Cost Service（Token 与成本统计）

**定位：** 将单次调用的 Token 与**估算成本**结构化，并支持多维度汇总。

**职责：**

1. **单次计算：** 根据模型单价配置与输入/输出 Token 计算估算成本；Token 未知时标记并采用约定 fallback。
2. **汇总查询：** 按日期、项目、业务类型、模型、用户等维度聚合（支撑 AC-5、AC-7）。
3. 为 **Cost Guard** 提供「当日已用成本」等判断依据。

**原则：** 估算成本仅用于运营观测，不作为财务结算唯一依据。

---

### 5.7 Failure Tracker（失败追踪）

**定位：** 对失败调用进行**分类、记录与统计**，支撑排障与策略优化。

**职责：**

1. 维护统一失败类型枚举（网络、超时、限流、认证、内容安全、参数、模型内部、未知等）。
2. 每次失败写入：请求编号、业务类型、模型链、失败类型、详情、重试次数、是否尝试过降级、时间。
3. 支撑管理端「失败统计」：按类型、模型、业务类型分布。

**与 Retry / Degradation：** 根据失败类型决定是否可重试、是否可降级；不可重试类快速失败并告警（认证类需人工处理配置）。

---

### 5.8 Retry Handler（重试）

**定位：** 在**同一计划模型**（或降级流程中的当前模型）上，对 transient 错误进行有限次重试。

**职责：**

1. 可重试：网络错误、超时、限流（退避）、部分模型内部错误。
2. 不可重试：认证、内容安全、参数、用户输入不合法等 — 立即失败并记录。
3. 记录每次重试的时间与结果；最终响应体现总重试次数。
4. 与限流、熔断、日成本上限协同，**禁止无限重试**。

**边界：** 重试耗尽后，由 **Degradation** 决定是否切换备用模型，而非 Retry 自行换模型。

---

### 5.9 Degradation Handler（模型降级）

**定位：** 当主模型路径失败且错误类型允许时，按配置**依次尝试备用模型**，对业务透明。

**职责：**

1. 触发条件：超时、限流、服务异常、重试后仍失败的模型内部错误等（与需求 4.3 对齐）。
2. 按业务类型的备用模型顺序调用 Model Client；保持**同一请求编号**。
3. 响应标明实际使用模型及是否降级；主模型失败仍记入失败追踪。
4. 所有备用均失败时，返回明确失败结果。

**不触发降级：** 认证错误、内容安全、参数错误等 — 换模型无法解决问题。

---

### 5.10 协作组件（限流、熔断、成本防护）

| 组件 | 职责 |
|------|------|
| **Rate Limiter** | 全局限流、按业务类型限流；触发时返回限流类失败并写日志 |
| **Circuit Breaker** | 某模型连续失败率超阈值则暂停新请求转发；优先走备用或快速失败；管理端可查看状态 |
| **Cost Guard** | 第一阶段：日全局成本上限；超限拒绝新调用并记录原因 |

## 六、AI 请求调用链路

### 6.1 主路径（成功）

```text
业务后端
    │  统一 AI 调用（含 businessType, projectId, userId?, input, params?）
    ▼
┌──────────────────────────────────────────────────────────────────┐
│ AI Gateway                                                        │
│  1. 校验请求语义，生成 requestId                                   │
│  2. Cost Guard：日成本是否超限？ ──是──► 失败返回 + 写日志          │
│  3. Rate Limiter：是否触发限流？ ──是──► 失败返回 + 写日志          │
│  4. Model Router：解析计划模型（主模型）                            │
│  5. Circuit Breaker：主模型是否熔断？ ──是──► 进入降级或备用路径   │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
                    ┌─────────────────┐
                    │  Model Client   │◄── Provider Adapter
                    │  调用计划模型    │
                    └────────┬────────┘
                             │ 成功
                             ▼
                    Token & Cost：计算 Token/估算成本
                    Invocation Logger：写入成功记录
                             ▼
                    Gateway：组装统一响应 → 业务后端
```

### 6.2 失败、重试与降级路径

```text
Model Client 返回失败（已映射失败类型）
    │
    ├─ 不可重试（认证/内容安全/参数等）
    │       ► Failure Tracker 记录
    │       ► Invocation Logger 记录失败
    │       ► Gateway 返回失败响应
    │
    └─ 可重试
            ▼
        Retry Handler（同一模型，有限次 + 退避）
            │
            ├─ 重试成功 ──► 写日志/成本 ──► 成功响应
            │
            └─ 重试仍失败
                    ▼
                是否允许降级？（按失败类型 + 配置）
                    │
                    ├─ 否 ──► 记录完整重试链 ──► 失败响应
                    │
                    └─ 是
                            ▼
                    Degradation Handler
                    按备用模型顺序循环：
                      Router 选定备用 → Model Client → Retry（每模型内）
                            │
                            ├─ 某一备用成功 ──► 标记降级成功、实际模型
                            │                  ► 写日志（含主模型失败信息）
                            │                  ► 成功响应（业务可见降级标识）
                            │
                            └─ 全部失败 ──► 记录降级链路 ──► 失败响应
```

### 6.3 管理端查询路径（观测）

```text
管理端 UI
    ▼
Admin / Observability API
    ├─ 调用日志列表/详情  ← Invocation Logger 查询
    ├─ Token/成本汇总     ← Token & Cost Service 聚合
    ├─ 失败分布           ← Failure Tracker 聚合
    ├─ 路由与熔断状态     ← Config Registry + Circuit Breaker 状态
    └─ 日成本上限配置     ← Cost Guard + Config Registry
```

### 6.4 关键贯穿标识

| 标识 | 用途 |
|------|------|
| **请求编号（requestId）** | 业务、底座日志、管理端详情统一对齐；AC-1 验收主键 |
| **业务类型（businessType）** | 路由、限流、统计维度 |
| **项目标识（projectId）** | 区分小红书 / 求职 Agent / 底座自身；AC-7 |
| **用户标识（userId，可选）** | 按用户成本与日志筛选（第一阶段统计预留） |

## 七、业务系统复用方式

### 7.1 复用原则

两个业务系统**不复制**底座能力，仅通过统一调用契约接入：

1. 业务后端在需要 AI 能力时，调用底座 **AI Gateway** 对外能力。
2. 每次调用必须携带正确的 **businessType** 与 **projectId**。
3. 业务侧负责：领域 Prompt/上下文组装、结果展示与「AI 生成需人工确认」提示。
4. 排障时以 **requestId** 在管理端与业务日志间关联。

### 7.2 小红书内容运营工作台

| 维度 | 说明 |
|------|------|
| **工程关系** | `xhs-mom-helper/backend` 依赖底座服务（进程内模块或 HTTP 调用方式在接口文档阶段确定；架构上视为**下游调用方**） |
| **projectId** | 固定为小红书项目枚举值（如 `xhs-mom-helper`，具体枚举 T-006 登记） |
| **典型 businessType** | 内容生成、标题生成、标签生成、内容复盘、文本总结等 |
| **路由期望** | 短文本/标签类偏低成本模型；正文生成、复盘分析可用高能力主模型 + 备用 |
| **业务不做** | 直连供应商；独立 Token 报表；独立降级重试 |

**第二阶段集成验证点：** 至少一种生成类调用端到端：业务 → 网关 → 日志可查（需求 AC-1～AC-2）。

### 7.3 智能求职 Agent 工作台

| 维度 | 说明 |
|------|------|
| **工程关系** | `smart-job-agent/backend` 同为下游调用方 |
| **projectId** | 固定为求职 Agent 项目枚举值（如 `smart-job-agent`） |
| **典型 businessType** | 岗位分析、经历匹配、面试准备、话术生成、文本总结等 |
| **路由期望** | JD 分析、深度匹配等复杂任务走高能力主模型；话术/短生成可配置较低成本默认 |
| **与 Agent 关系** | Agent **编排**（多步任务、工具调用）归属业务域；每一步 LLM 需要仍**逐步调用 Gateway**，底座不实现 Agent 状态机 |

### 7.4 统计与隔离

管理端与汇总接口通过 **projectId** 区分两业务消耗；通过 **businessType** 分析场景占比。底座自身运维调用可使用独立 projectId，避免与业务混淆。

### 7.5 前端边界

| 系统 | AI 相关前端行为 |
|------|-----------------|
| 小红书 / 求职前端 | 只调各自业务 API；展示 AI 结果与 requestId（可选，便于排障） |
| 底座管理端 | 日志、成本、失败、配置 — 第一阶段 MVP 页面见产品文档 |

## 九、第一阶段：做什么

> 全项目第一阶段 = 通用 AI 技术底座。与需求文档第七章、验收 AC-1～AC-7 对齐。

### 9.1 必须交付的架构能力

| 序号 | 能力 | 架构落点 |
|------|------|----------|
| 1 | 统一 AI 网关 | AI Gateway 完整编排链路 |
| 2 | 多模型路由 | Model Router + 静态配置 |
| 3 | 模型降级 | Degradation Handler + 主备配置 |
| 4 | 调用日志 | Invocation Logger + 持久化 + 列表/详情查询 |
| 5 | Token 统计 | Token & Cost Service 单次 + 汇总 |
| 6 | 成本统计 | 同上 + Cost Guard 日上限 |
| 7 | 失败追踪 | Failure Tracker + 分类与聚合 |
| 8 | 重试 | Retry Handler |
| 9 | 基础限流 | Rate Limiter（全局 + 按业务类型） |
| 10 | 基础熔断 | Circuit Breaker + 管理端可查看 |
| 11 | 基础可观测 | Admin：日志、成本、失败、设置（产品 MVP 页面） |

### 9.2 成本控制 subset（第一阶段）

1. 每日全局成本上限（可配置，管理端可改）。
2. 按业务类型查看成本占比。
3. 超限时拒绝新调用并记录原因。

月上限、单用户上限、高成本模型精细限制的**完整 UI** 可末期或第二阶段初补齐；架构上 Cost Guard 与 Router 预留扩展点。

### 9.3 业务类型与项目标识（登记）

第一阶段在配置层登记至少：

- **项目：** `xhs-mom-helper`、`smart-job-agent`（及底座自身若需要）
- **业务类型：** 需求文档 4.1.4 示例集合中的各场景，保证可独立路由、统计、限流

具体枚举固化在 T-006，与本文档一致。
