## 二、建设目标与价值

### 2.1 建设目标

建设一套可复用的 AI 应用基础设施，为所有业务系统提供统一的大模型调用与管理能力。

核心目标：

1. **降低耦合**：业务代码不直接依赖具体模型供应商
2. **统一入口**：所有 AI 请求经同一网关进入
3. **统一观测**：调用日志、Token、成本、失败原因集中记录与查看
4. **统一韧性**：路由、降级、重试、限流、熔断由底座承担
5. **避免重复建设**：两个业务系统共用同一套 AI 基础能力

### 2.2 业务价值

| 价值点 | 说明 |
|--------|------|
| 可维护性 | 模型切换、策略调整集中在底座，业务侧改动最小 |
| 可观测性 | 任意一次 AI 调用可追溯到请求、模型、耗时、成本、结果 |
| 可用性 | 主模型失败时可降级，减少对业务流程的中断 |
| 成本可控 | 多维度统计与上限控制，避免调用失控 |
| 合规与安全 | 统一记录与审计，便于排查异常调用 |

## 三、使用方与调用关系

### 3.1 使用方

| 使用方 | 角色 |
|--------|------|
| 小红书内容运营工作台 | 业务调用方：内容生成、标题/标签生成、复盘分析等 |
| 智能求职 Agent 工作台 | 业务调用方：岗位分析、匹配分析、面试准备、话术生成等 |
| 底座管理端 | 运维/开发者：查看日志、成本、失败统计、策略配置 |

### 3.2 调用原则

1. **所有 AI 请求必须经过统一 AI 网关**，业务模块不得直接调用具体模型 API。
2. 业务系统提交请求时需携带**业务类型标识**，供路由与统计使用。
3. 业务系统只消费网关返回的统一结果语义，不关心底层供应商差异。
4. 底座对业务系统**透明处理**降级与重试（在策略允许范围内），业务侧无需重复实现。

### 3.3 调用关系示意

```text
业务系统（小红书 / 求职 Agent）
        │
        ▼
  统一 AI 网关
        │
   ┌────┴────┐
   ▼         ▼
模型路由   调用日志 / 成本统计 / 失败追踪
   │
   ▼
模型供应商（经适配层屏蔽差异）
```

## 四、核心能力需求

### 4.1 统一 AI 网关

#### 4.1.1 职责

1. 作为所有大模型调用的**唯一入口**
2. 屏蔽不同模型供应商之间的请求/响应差异
3. 为业务模块提供**统一、稳定的调用语义**

#### 4.1.2 请求语义（需求层）

业务调用方在发起请求时应能表达：

| 要素 | 说明 |
|------|------|
| 业务类型 | 标识本次调用的业务场景，用于路由与统计 |
| 用户标识 | 可选，用于按用户统计成本与日志 |
| 项目标识 | 可选，用于区分小红书 / 求职 Agent 等项目维度 |
| 输入内容 | 本次 AI 任务所需的文本或结构化输入 |
| 扩展参数 | 如温度、最大输出长度等（由底座统一约束与转发） |

#### 4.1.3 响应语义（需求层）

网关向业务方返回的结果应包含：

| 要素 | 说明 |
|------|------|
| 请求编号 | 全局唯一，用于追溯与对账 |
| 调用状态 | 成功 / 失败 / 降级成功等 |
| 输出内容 | 模型生成的文本或结构化结果 |
| Token 消耗 | 输入、输出、合计（若供应商可提供） |
| 估算成本 | 基于 Token 与模型单价估算 |
| 调用耗时 | 端到端耗时 |
| 实际使用模型 | 含降级后的实际模型名称 |
| 失败信息 | 失败时提供可读原因分类 |

#### 4.1.4 业务类型标识（示例）

底座需支持按业务场景区分调用，典型业务类型包括：

| 业务类型（示例） | 所属系统 | 典型用途 |
|------------------|----------|----------|
| 内容生成 | 小红书 | 正文生成 |
| 标题生成 | 小红书 | 标题生成 |
| 标签生成 | 小红书 | 话题标签生成 |
| 内容复盘 | 小红书 | 发布后数据分析与建议 |
| 岗位分析 | 求职 Agent | JD 结构化分析 |
| 经历匹配 | 求职 Agent | 个人与岗位匹配分析 |
| 面试准备 | 求职 Agent | 面试题与回答思路 |
| 话术生成 | 求职 Agent | 打招呼语、求职信等 |
| 文本总结 | 通用 | 长文本摘要 |
| 文本分类 | 通用 | 内容分类 |

具体枚举可在架构阶段固化；需求阶段要求：**每种业务场景可独立路由、统计、限流**。

---

### 4.2 多模型路由

#### 4.2.1 目标

根据不同**业务类型**和**任务复杂度**，自动选择合适的主模型；支持主备模型配置。

#### 4.2.2 路由策略需求

| 策略 | 说明 |
|------|------|
| 按业务类型路由 | 不同业务类型可配置不同默认模型 |
| 低成本优先 | 对简单任务（如标签生成、短摘要）优先使用低成本模型 |
| 高能力优先 | 对复杂分析（如岗位分析、深度匹配）使用高能力模型 |
| 主备模型 | 每个业务类型可配置主模型与至少一个备用模型 |

#### 4.2.3 路由决策输入

路由应至少考虑：

1. 业务类型
2. 是否允许使用高成本模型（可由成本控制策略约束）
3. 主模型当前可用性（结合降级逻辑）

#### 4.2.4 路由结果记录

每次调用需记录：

1. 路由命中的业务类型
2. 计划使用的模型
3. 实际使用的模型（若发生降级则记录最终模型）

---

### 4.3 模型降级

#### 4.3.1 目标

当主模型不可用或调用失败时，自动切换备用模型，减少对业务流程的影响。

#### 4.3.2 触发条件

以下情况应触发降级评估（在可重试错误仍失败或不可重试但属于服务侧问题时）：

| 条件 | 说明 |
|------|------|
| 请求超时 | 超过配置的超时阈值 |
| 限流错误 | 供应商返回限流 |
| 服务异常 | 模型服务不可用、5xx 类错误 |
| 模型返回失败 | 模型内部错误且重试无效 |

#### 4.3.3 降级行为需求

1. 按业务类型配置的备用模型顺序依次尝试
2. 降级过程对业务调用方**透明**（同一请求编号下完成）
3. 响应中标明**实际使用模型**及是否发生降级
4. 降级事件计入调用日志与失败追踪（主模型失败仍记录）

#### 4.3.4 边界

1. 认证错误、内容安全错误、参数错误等**不应**通过换模型解决
2. 所有备用模型均失败时，向业务方返回明确失败结果

---

### 4.4 调用失败追踪

#### 4.4.1 目标

记录每一次失败调用的原因，支持统计、排查与策略优化。

#### 4.4.2 失败类型分类

| 失败类型 | 说明 | 典型处理方向 |
|----------|------|--------------|
| 网络错误 | 连接失败、DNS、断连等 | 可重试 |
| 请求超时 | 超过超时时间 | 可重试 / 可降级 |
| 限流错误 | 供应商或底座限流 | 可重试 / 可降级 |
| 认证错误 | API Key 无效、权限不足 | 不可重试，需人工处理配置 |
| 内容安全错误 | 输入或输出触发安全策略 | 不可重试，需业务侧调整输入 |
| 参数错误 | 请求参数不合法 | 不可重试，需修正调用方 |
| 模型内部错误 | 供应商侧未知或内部错误 | 可重试 / 可降级 |
| 未知错误 | 无法归类的错误 | 记录原始信息，按策略处理 |

#### 4.4.3 失败记录要素

每次失败至少记录：

1. 请求编号
2. 业务类型
3. 模型名称（含降级尝试链）
4. 失败类型
5. 失败详情（可读描述，不含敏感密钥）
6. 重试次数
7. 是否已尝试降级
8. 发生时间

---

### 4.5 重试机制

#### 4.5.1 目标

对 transient 错误自动重试，提高成功率；对确定性错误快速失败。

#### 4.5.2 可重试错误

| 错误类型 | 默认策略 |
|----------|----------|
| 网络错误 | 重试，次数与间隔可配置 |
| 请求超时 | 重试，次数可配置 |
| 限流错误 | 退避重试 |
| 部分模型内部错误 | 有限次重试后进入降级 |

#### 4.5.3 不可重试错误

| 错误类型 | 说明 |
|----------|------|
| 认证错误 | 立即失败并告警 |
| 内容安全错误 | 立即失败，返回业务可读提示 |
| 参数错误 | 立即失败，记录调用方问题 |
| 用户输入不合法 | 由业务校验优先拦截；若到达网关则失败返回 |

#### 4.5.4 重试记录需求

1. 记录每次重试的时间与结果
2. 最终响应中可体现**总重试次数**
3. 重试与降级、限流策略协同，避免无限重试

---

### 4.6 Token 与成本统计

#### 4.6.1 目标

统一统计所有 AI 调用的 Token 消耗与估算成本，支持多维度查询与分析。

#### 4.6.2 统计维度

| 维度 | 说明 |
|------|------|
| 按用户 | 单用户 Token 与成本汇总 |
| 按业务类型 | 各场景消耗占比 |
| 按模型 | 各模型使用量与成本 |
| 按日期 | 日粒度趋势 |
| 按项目 | 小红书 / 求职 Agent / 底座自身 |

#### 4.6.3 统计指标

| 指标 | 说明 |
|------|------|
| 输入 Token | 单次或汇总 |
| 输出 Token | 单次或汇总 |
| 总 Token | 输入 + 输出 |
| 调用次数 | 成功与失败可区分 |
| 估算成本 | 基于模型单价与 Token 估算 |
| 平均耗时 | 成功调用的平均响应时间 |
| 失败次数 | 按失败类型可细分 |

#### 4.6.4 成本估算原则（需求层）

1. 每种模型配置单位 Token 价格（输入/输出可分别配置）
2. 无法获取 Token 时，记录调用并标记「Token 未知」，成本可按次估算或置空
3. 估算成本用于**运营观测**，不作为财务结算唯一依据

### 4.7 调用日志

#### 4.7.1 目标

每一次 AI 调用（含失败、降级、重试）均留下可追溯记录。

#### 4.7.2 日志记录要素

| 字段 | 说明 |
|------|------|
| 请求编号 | 全局唯一 |
| 用户标识 | 可选 |
| 项目标识 | 业务系统来源 |
| 业务类型 | 路由与统计用 |
| 计划模型 | 路由初选模型 |
| 实际模型 | 含降级后最终模型 |
| 调用状态 | 成功 / 失败 / 降级成功 |
| 输入 Token | 数值或未知 |
| 输出 Token | 数值或未知 |
| 估算成本 | 数值或未知 |
| 调用耗时 | 毫秒级 |
| 失败类型 | 失败时填写 |
| 失败详情 | 失败时填写 |
| 重试次数 | 含重试与降级尝试 |
| 是否降级 | 是 / 否 |
| 创建时间 | 调用完成时间 |

#### 4.7.3 日志使用场景

1. 排查单次调用问题
2. 分析某业务类型调用量与成功率
3. 审计高成本调用
4. 对接开发计划中的进度与问题记录

---

### 4.8 限流与熔断

#### 4.8.1 限流需求

在以下层面提供基础限流能力（具体阈值可配置）：

| 层面 | 目的 |
|------|------|
| 全局限流 | 保护底座与供应商不被突发流量击垮 |
| 按业务类型限流 | 防止单一场景占用过多配额 |
| 按用户限流 | 防止单用户异常调用 |

限流触发时：

1. 返回明确限流类失败
2. 记录失败日志
3. 不计入成功调用，可计入失败统计

#### 4.8.2 熔断需求

当某模型或供应商连续失败率达到阈值时：

1. 暂时停止向该模型转发新请求
2. 优先走备用模型或快速失败
3. 熔断状态可查看（管理端）
4. 恢复条件：冷却时间后探测或手动恢复（产品层支持查看即可）

---

### 4.9 成本控制

#### 4.9.1 目标

提供基础成本防护，避免 Token 与费用失控。

#### 4.9.2 控制策略需求

| 策略 | 说明 |
|------|------|
| 每日成本上限 | 全局或分项目日上限，超限后拒绝或仅允许低成本模型 |
| 每月成本上限 | 同上，月粒度 |
| 单用户成本上限 | 按用户维度封顶 |
| 单业务类型上限 | 防止单场景滥用 |
| 高成本模型限制 | 超阈值时禁止或需显式放开 |
| 低成本模型优先 | 与路由策略联动 |

#### 4.9.3 超限行为

超限时向调用方返回可读失败原因（成本超限类），并记录日志；不静默丢弃请求。

---

### 4.10 可观测能力

#### 4.10.1 目标

为开发者/运维提供基础查看能力，无需依赖外部 APM 即可完成日常排查。

#### 4.10.2 查看能力清单

| 能力 | 说明 |
|------|------|
| 调用记录列表 | 按时间、业务类型、状态筛选 |
| 调用详情 | 单次请求完整要素 |
| Token 消耗汇总 | 多维度汇总与趋势 |
| 成本统计 | 与 Token 联动展示 |
| 模型成功率 | 按模型统计成功/失败比 |
| 失败原因分布 | 按失败类型聚合 |
| 业务模块调用占比 | 各业务类型调用量占比 |
| 模型调用耗时 | 平均/分位耗时（第一阶段至少平均值） |
| 降级发生记录 | 可筛选发生过降级的调用 |

## 五、非功能需求

| 类别 | 要求 |
|------|------|
| 可用性 | 主模型故障时通过降级与重试提高整体调用成功率 |
| 可追溯性 | 任意调用可通过请求编号关联日志、成本与失败信息 |
| 可审计性 | 日志保留足够要素，支持事后复盘（保留周期在部署文档定义） |
| 扩展性 | 可新增业务类型、模型供应商、路由规则而不改动业务系统 |
| 一致性 | 同一业务类型在相同配置下路由行为可预期 |
| 安全性 | 密钥等敏感信息不得写入业务可见日志详情 |
| 性能 | 底座自身开销应明显小于模型调用耗时（具体指标在架构/测试阶段定义） |

## 六、与业务系统的关系

### 6.1 业务系统依赖底座的能力

两个业务系统共用：

1. 统一 AI 网关
2. 模型路由与降级
3. AI 调用日志
4. Token 与成本统计
5. 失败追踪
6. 重试、限流、熔断

### 6.2 业务系统禁止事项

1. 不得绕过网关直接调用模型 API
2. 不得自行维护独立的 Token/成本统计（应使用底座数据）
3. 不得复制一套降级/重试逻辑替代底座（业务侧仅可做输入校验与结果展示）

### 6.3 业务系统需配合的事项

1. 为每次 AI 调用传入正确的**业务类型**与**项目标识**
2. 在 UI 中可嵌入或链接底座的日志/成本查看（或由统一管理端查看）
3. 对用户可见的 AI 结果需标注「AI 生成，需人工确认」（业务产品文档约定）

## 七、第一阶段：做什么

> **说明：** 此处「第一阶段」指**全项目第一阶段**，对应当前 README 与开发计划中的「通用 AI 技术底座」建设阶段。

### 7.1 阶段目标

完成两个业务系统共用的 AI 基础能力，形成统一调用入口、日志、成本、失败处理与基础可观测。

### 7.2 本阶段交付的能力

| 序号 | 能力 | 交付说明 |
|------|------|----------|
| 1 | 统一 AI 网关 | 业务系统可通过统一语义发起调用并获得统一响应 |
| 2 | 多模型路由 | 按业务类型选择主模型，支持主备配置 |
| 3 | 模型降级 | 主模型失败时自动尝试备用模型 |
| 4 | 调用日志 | 每次调用完整记录，支持列表与详情查看 |
| 5 | Token 统计 | 按调用记录 Token，支持多维度汇总 |
| 6 | 成本统计 | 基于 Token 估算成本，支持多维度汇总 |
| 7 | 失败追踪 | 失败类型分类与统计 |
| 8 | 重试机制 | 对可重试错误自动重试 |
| 9 | 基础限流 | 全局与按业务类型限流 |
| 10 | 基础熔断 | 模型连续失败时暂停转发 |
| 11 | 基础可观测页面 | 日志、成本、失败分布、模型使用情况查看 |

### 7.3 第一阶段成本控制 subset

本阶段实现以下 subset 即可验收：

1. 每日全局成本上限（可配置）
2. 按业务类型查看成本占比
3. 超限时拒绝新调用并记录原因

月上限、单用户上限、高成本模型精细限制可放在第一阶段末期或第二阶段初补齐。

### 7.4 验收标准（业务可测）

| 编号 | 验收项 |
|------|--------|
| AC-1 | 业务系统发起一次 AI 调用后，可在日志列表中按请求编号查到该记录 |
| AC-2 | 成功调用记录包含业务类型、模型、Token、耗时、估算成本 |
| AC-3 | 模拟主模型失败后，同一请求可降级成功或明确记录降级链路与最终失败 |
| AC-4 | 失败调用可按失败类型筛选与统计 |
| AC-5 | 可按日期、业务类型、模型查看 Token 与成本汇总 |
| AC-6 | 触发限流或日成本上限时，调用方收到明确失败原因且产生日志 |
| AC-7 | 两个业务项目标识的调用在统计中可区分 |
